## 3. What was implemented (offline)
- `restricted_route.py`: an exact two-route table (POOLER, DIRECT). DIRECT is `db.zcikcfgpblzuzpanpdqd.supabase.co:5432/postgres` with the **plain role** as username. The administrative route (pooler, `postgres.<ref>`) and the production application's settings are untouched.
- `runtime_principal(url, ssl, route)` / `DatabaseBudget.engine(..., route=)`: the principal must match the one registered route exactly (host, port, database, username form, role, `verify-full` with the checked-in CA); any other route raises `RESTRICTED_ROUTE_MISMATCH`. The Runner always passes its route; there is no fallback path. (The consumed matrix controller still calls without a route and is left unchanged.)
- Preparation: a second, bounded, credential-free **IPv4-only** resolution of the direct host; the restricted engines are pinned to that address and **never** to the administrative pooler address (`DIRECT_ROUTE_ADDRESS_REQUIRED` otherwise). `host=` carries the real hostname, so certificate and hostname verification use it.
- Mode `DIRECT_ROUTE_DIAGNOSTIC_ONLY`: reuses the finite diagnostic path (setup → qualification → teardown) with matrix-class timing, its own finite administrative limits, **no policy application** and exactly one permitted installed state (the retained successor-policy inventory). The registration binds route, mode, authority, all three consumed predecessors by hash, limits, expiry (≤ 2 h), `execution_authority: NONE`, and no settling period.
- Package `docs/design/ingestion-direct-route-diagnostic-20261020/` (renderer, owner script, manifest) and tests.

## 4. Complete behaviour of the diagnostic path (effects stated explicitly even though it issues no grant)
Read-only preflight (plus a rolled-back transaction); restore the two reviewed capability memberships; capture and set the three role-level timeouts; **set a fresh password with `VALID UNTIL` on both restricted logins; create two temporary protected secrets (two GitHub writes); enable `LOGIN` on both logins**; one worker connection attempt, one effect attempt only if the worker succeeds; then, in every outcome, teardown (`NOLOGIN`, NULL password, memberships revoked, role settings restored, secrets deleted, closure checks). It registers no authority or Bolton exception, makes no source request, writes no queue row and does not apply the policy. Two restricted logins are therefore enabled for new connections between setup and teardown, as in every earlier run.

## 5. Validation
- **Disposable PG17 lifecycle (hosted):** success (65 administrative commands / 5 connections; worker then effect, one attempt each; control row, ledger and roles unchanged afterwards; secrets removed; settings restored; connection, process and access closure separately verified); worker rejected (72 / 6; effect never attempted); effect rejected after the worker connected (72 / 6; teardown still complete); pooler-form URL refused before any restricted contact; missing direct address refused before any contact; no restricted contact ever leaves the direct route or uses the administrative address.
- **Real TLS (loopback server with real certificates):** the direct hostname's certificate is accepted when it matches and chains to the pinned trust; a certificate for another hostname fails with `TLS_HOSTNAME_MISMATCH`; an untrusted chain fails with `TLS_CHAIN_REJECTED`.
- **Offline compatibility only.** Not proved: that the production endpoint's certificate chains to the checked-in CA and matches the hostname, that custom roles authenticate there as in the disposable server, and that the add-on makes the host reachable from the owner's WSL and from Render.
- **Independent review:** one focused review; no blocking finding. Fixed: strict integer check for the no-settling binding, an effect-rejection rehearsal and extra registration negatives. Disclosed, not changed: `route=None` remains accepted by the legacy matrix call path; and the diagnostic has **no settling period** (the pooler runs used one), so a failure here would not be a delay experiment — it would be about the direct route itself.

## 6. Single production proposal (one grouped decision; not released)
1. **Owner action first (dashboard, not a repository change):** move the organisation from Free to Pro and enable the dedicated IPv4 add-on. Recurring cost per Supabase: Pro from $25/month plus about $4/month for the add-on (dashboard prices at activation govern; IPv4 hours sit outside the spend cap). Nothing is purchased by this document.
2. **DNS / network impact:** enabling the add-on replaces the direct host's IPv6 record with an IPv4 record (brief direct-connection downtime, under a minute per Supabase). No restriction exists today, so the database will accept direct connections from any IPv4 address (SCRAM and `verify-full` still apply); network restrictions could narrow that later. **Existing consumers:** the production application uses the pooler (per the repository's own documentation), the administrative route is the pooler, and no repository code uses the direct host; unverified: any external tool of the owner's using the direct IPv6 host. The shared pooler is unaffected.
3. **Integration:** PR #150 with guarded `[skip render]` commits, combined-tree and executable-hash reconciliation, required checks (the same procedure as before). 
4. **Registration:** one fresh registration, rendered from the integrated revision with the current evidence-branch head, expiring within 110 minutes; the owner script refuses to start while the direct host has no IPv4 address, while the namespace or any predecessor audit differs, or while the scope state is unreadable.
5. **Run (owner terminal, hidden input only in the owner's own visible terminal):** the effects in section 4; one connection attempt per role; administrative budget ≤ 60 / 80 / 92 commands over ≤ 5 / 6 connections; hidden input 120 s, active window 270 s, work alarm 215 s, outer 420 s, backstop 450 s; 1 preparation GitHub call plus the lifecycle's writes.
6. **Pass criteria:** both logins connect on their first attempt to the direct host over verified TLS to the pinned IPv4 address; identity, flags and effective timeouts match; teardown ends with both logins `NOLOGIN` and NULL password, no memberships or sessions, role settings restored, both secrets deleted, and connection, process and access closure `CLOSED`; no grant, source request or queue row. **Fail:** any rejection or TLS error stops and tears down; there is no retry, no settling experiment and no fallback to the pooler or to option B.
7. **Not authorised by a pass:** a Bolton capture, screening or any grant would be a separate decision (and a separate direct-route capture mode is not implemented here).
8. **Re-bound for this finite diagnostic only:** the previously reviewed temporary-credential (possible SCRAM verifier retention) acceptance.
