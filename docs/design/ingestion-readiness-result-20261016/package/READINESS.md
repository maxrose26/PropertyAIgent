## Exact additive migration and access boundary

`migration.sql` is the first-install administrator transaction, not an instruction to execute now. It creates exactly two existing-design ledger tables, five NOLOGIN/NOSUPERUSER/NOBYPASSRLS roles, FORCE RLS policies and two narrowly scoped functions; it initializes the control row with the consumed Salford global stop and empty grants. Any pre-existing named table, role or function causes rollback; do not replace it blindly or run the earlier install() over this ownership/policy layout. Compare schema types/defaults/constraints, function definitions/owners/search_path, ACLs and RLS against the reviewed SQL. No Application schema or rows change.

| Capability role | Permitted now | Explicitly unavailable |
|---|---|---|
| ingestion_storage_owner | NOLOGIN owner used only by two SECURITY DEFINER functions; full policy on ledger | No membership granted, no application-table rights, no BYPASSRLS |
| ingestion_storage_operator | Read both tables; invoke fixed three-item seed; raise stop | Arbitrary enqueue/update/delete, attempts, claims, source/write grants, release |
| ingestion_worker | Read both tables; raise stop | Insert/update/delete/claim/checkpoint/attempt creation, seed, authority issuance, release, application writes |

| ingestion_barrier_releaser | NOLOGIN placeholder with no object grants or functions | All barrier release; no worker/issuer membership |

Only SELECT policies apply to worker/operator. Owner has a separate policy because FORCE RLS also binds non-BYPASS owners. The privileged migration uses pg_catalog first and explicitly qualifies ledger DDL; the test injects a public shadow function to verify it is not invoked. Function search_path is pg_catalog; references are schema-qualified. All pre-existing default ACL grants to non-owner roles are normalized away on both tables/functions before granting the specified allowlist; PUBLIC EXECUTE is revoked; no arbitrary SQL/JSON input is accepted by seed. Stop accepts only a nonempty <=512-byte reason, preserves the original stop and records the latest manual reason; release has no API. No new login, secret, role membership, CONNECT privilege or runtime credentials are installed by this SQL. A production administrator must separately attest least-privilege login membership, no inherited owner/admin/service-role rights, no application DML rights, no CREATE in a trusted function schema, and deny untrusted Data API exposure of these tables/functions. Superuser and database-admin access remain outside this worker trust boundary.

Operational worker execution is deliberately denied at the database, independently of Python. Granting broad UPDATE to make Ledger work would also allow authority forgery in the combined CONTROL row. Therefore production task execution requires a later reviewed transactional RPC boundary (or equivalent restricted controller isolation) for claim/checkpoint/finish/intent/recovery, with worker, issuer and barrier-release capabilities separated. It is not delivered or silently enabled here. This is a concrete operational acceptance blocker, not a production-ready worker claim.

`test_pg_storage_acceptance_intended_restricted_role` installs this exact SQL in disposable PostgreSQL, authenticates separate non-owner worker/operator logins with the intended group-role memberships, checks current_user and NOSUPERUSER/NOBYPASSRLS/NOCREATEROLE, seeds twice, reconnects and verifies exact rows. It denies seed to worker, arbitrary enqueue, claim UPDATE, control overwrite, attempt insert, deletion, truncation, RLS disable, owner/issuer/releaser impersonation and Application UPDATE. No superuser connection is used for these denial assertions. The test injects adverse administrator default privileges granting all tables/functions to a separate BYPASSRLS login and verifies that login still cannot access the new objects after ACL normalization. Administrator credentials are used only to create/tear down disposable objects. This tests the storage role, not an operational claim RPC or actual production credentials.

## Connection, pooler and transaction contract

Repository app/db/models.py documents the existing production Supabase transaction pooler; app/db/session.py normalizes postgresql:// to psycopg3 but defaults to a generic engine. Do not reuse that generic engine or load .env implicitly for this controller. Actual production hostname, PostgreSQL/pooler version, role mapping, certificate trust, RLS and connection limits were not probed under this authority.

Proposed manual storage client: explicit approved secret reference and allowlisted destination/database/login, psycopg3, sslmode=verify-full with deployment CA, connect_timeout=3, prepare_threshold=None, SQLAlchemy NullPool, one connection at a time, READ COMMITTED, UTC, no application credentials. Disable automatic reconnect/retry; a disconnect is an uncertain transaction until readback. One transaction per seed/stop; readbacks in new read-only transactions, explicitly closed. Set LOCAL statement_timeout=10s, lock_timeout=3s and idle_in_transaction_session_timeout=10s inside each transaction. Do not rely on connection `options` support in the real pooler. No session advisory locks, temporary tables, session SET ROLE or session state spanning transactions. Production migration uses a dedicated approved administrator/direct or session connection, not a transaction-pooler session role change.

Psycopg official prepared-statement guidance supports disabling preparation with prepare_threshold=None: https://www.psycopg.org/psycopg3/docs/advanced/prepare.html . PostgreSQL owner/FORCE-RLS semantics: https://www.postgresql.org/docs/current/ddl-rowsecurity.html . These explain the proposed configuration, not proof of actual production compatibility. Disposable reconnection/transaction tests do not emulate all PgBouncer behaviour. Before production acceptance verify the selected endpoint accepts TLS/role authentication/SET LOCAL and does not expose these objects through unrelated roles. Failure means stop, no fallback to a stronger role.

Current ledger uses a control-row FOR UPDATE lock and local 3s/10s lock/statement timeouts. Decisions, fence/attempt reservation and checkpoints commit together. The shared writer uses a separate transaction while the ledger lock is held: later operational composition must budget at most TWO concurrent DB connections, one ledger and one B2, bound the writer's entire wall time, and prevent another claimant from waiting beyond lock timeout. No database-wide exactly-once effect is claimed. A timeout/disconnect around writer commit requires independent reconciliation; WRITE_INTENT remains a global barrier. The storage test has no writer connection and no source worker.
