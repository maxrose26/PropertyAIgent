**Selection.** `Coordinator(..., screening_rules=None)`; the default registry is `{'listing-screen-v1': v1}` and behaves byte-identically to master. v3 is selected only by registering `{'listing-screen-v3': Rule(RULE_V3, config)}` with an explicit config (threshold passed in, never read ambiently) **and** enqueuing children under that contract. An unregistered contract is denied (`SCREENING_CONTRACT_NOT_REGISTERED`). A run registers one screening contract (so v1 and v3 are never mixed within a run; recommendation R2).

## 3. Assessment identity (corrected)

An assessment is identified by **what was assessed** and **how**:
- `record_sha256 = digest(record)`: the source record, kept **separately identifiable** (unchanged from today's v1 `revision`).
- `config` = `{rule_version, count_spec_version: 'residential-count-v2', assessor: 'count_assessment', unit_threshold, max_text_chars}`; `config_sha256 = digest(config)`. Every decision-affecting parameter is in `config`, so a changed threshold changes it.
- v3 item: `contract = 'listing-screen-v3'`, `revision = digest({record_sha256, config_sha256})`, so `key = digest(subject, 'SCREENING', contract, revision)`.

Consequences: identical inputs give the same key, so `enqueue` returns the existing item (**idempotent**); a changed threshold (or any config field) gives a **distinct** item and assessment; the same record under v1 and v3, or under two thresholds, are three items with the same `record_sha256`. At screening time the coordinator recomputes `record_sha256` from the immutable capture, rebuilds `config` from the registry and requires `digest({...}) == row['revision']` (else `SCREENING_IDENTITY` / `SCREENING_CONFIG_BINDING`), so an item enqueued under one configuration can never be answered under another.
The v3 checkpoint carries `record_sha256`, `config`, `config_sha256`, `assessment_revision` (the item revision), `assessment_sha256 = digest(count_assessment)`, `capture_key`, `capture_sha256`, plus the existing source fields (`source_url`, `source_record_id`, `source_sha256`). v1 items are unchanged.
*Limit, stated:* a change to the assessor's behaviour under the same `rule_version` and `config` would collide with stored items; behaviour changes require a new rule version (the existing immutable-version convention, already enforced by the golden-digest tests).

## 4. History: link, never supersede

At screening time the coordinator records `related_assessments`: for every other SCREENING item with the same `subject` and `record_sha256`, `{item_key, contract, rule_version, config_sha256, relation: 'OTHER_ASSESSMENT_OF_SAME_RECORD'}`. It **never** sets or implies `supersedes`, never marks any assessment "current" or "latest", and never edits an earlier item (immutable once COMPLETE). A newer screening version **does not supersede the underlying factual evidence**: the capture, observation, record digests and history entries are untouched; a screening version is a derived classification. Any supersession of a decision or a count is a separate, explicit, recorded act (owner assessment in 035 D10; decision history in 036 section 8). Consumers act on the specific screening item they are given (the identity task's dependency), so there is no implicit "newest wins".

## 5. Routing and the identity gates

`identity_admission_eligible(result)` returns true only for: v1 `SUPPORTED_PROCESSING_PRIORITY` / `RELATED_APPLICATION_FOLLOW_THROUGH` (as today), and v3 `ADMIT_SCHEME` / `ADMIT_FOR_ASSESSMENT` (via `routing_of`, never the informational `disposition`); any `ValueError` means false. **Eligibility is only the first condition.** An eligible result must still pass every existing check in `new_identity.execute`: the screening parent is COMPLETE, a SCREENING task for the identical subject, the source URL/record-id binding, the qualified projector and factual verification (`b2_eligible`, verification scope, coupled gate), and `admit_identity`'s own idempotent pending-identity transaction. **Neither outcome writes a count or confirms scheme qualification**: result stays `unit_facts: NOT_WRITTEN`, `unit_confirmation_status = 'discovery_pending'`, `estimated_unit_count` NULL, no `SchemeIntelligence`, no Site link.
`ROUTE_COUNT_UNCONFIRMED`, `RETAIN_RELATED_TO_PARENT`, `RETAIN_BELOW_THRESHOLD`, `RETAIN_NOT_RESIDENTIAL_SUPPLY`, `RETAIN_WATCHLIST` and `RETAIN_UNUSABLE_PROPOSAL` are never eligible for an identity (`SELECTIVE_SCREENING_REQUIRED`); they are retained with their evidence.

## 6. Projections (read-only, pure; only what the flow needs)

- `assessment_history(items, subject, record_sha256)`: every SCREENING item for that record with `rule_version`, `config_sha256`, `routing_of` authority/outcome and the `related_assessments` links, in a stable sort (`rule_version`, `config_sha256`, `item_key`) that implies no recency or precedence.
- `investigation_requirements(items)`: one entry per v3 result that needs investigation, with `subject`, `assessment_item`, `record_sha256`, `requirement_kind`, `reason`, `parent_context` (reference, relation; any parent figure labelled `CONTEXT_ONLY`), and **`executable: false`, `executor: 'NONE'`** with the note *"recorded requirement; no executor exists for ledger-held identities"*. Kinds: reserved matters without a count (`RESERVED_MATTERS_WITHOUT_STATED_COUNT`) -> `PARENT_REFERENCE_RESOLUTION` + `COUNT_FROM_PHASE_DOCUMENTS`; count-unconfirmed (`RESIDENTIAL_WITHOUT_STATED_COUNT`, `MIXED_USE_WITHOUT_STATED_RESIDENTIAL_COUNT`) -> `COUNT_CONFIRMATION`; ambiguous wording (`AMBIGUOUS_PER_GROUP_COUNT`, `COUNT_WORDING_NOT_PARSED`, `MULTIPLE_PROPOSED_DWELLING_COUNTS`, `STUDENT_ACCOMMODATION_IN_MIXED_SCHEME`, `POSSIBLE_BREAKDOWN_OF_A_TOTAL`, `REPEATED_COUNT`) -> `COUNT_CLARIFICATION`; `ADMIT_FOR_ASSESSMENT` (qualified maximum, conflict) -> `TARGETED_DOCUMENT_EXTRACTION`. The legacy stages (`stage_fetch_missing_parents`, `stage_confirm_units`) act only on `Application` rows and are **not** connected; the projection labels nothing executable. **A recorded requirement is not an executable task**; creating one needs a new task kind, SQL worker support, privileges and source authority (Phase B, held). The owner-only review workspace (036) is not built; this projection is the read-side input it will later consume.

## 8. Acceptance criteria (offline, disposable SQLite ledger)

*Compatibility:* default registry gives v1 results byte-identical to master (the V1 golden digest extended through the Coordinator); existing screening, batching and new-identity suites unchanged; the 62 examples unchanged; consumed Stage 4 package tests unaffected (if a package manifest pin trips on `coordinator.py`/`new_identity.py`, reconcile by the archive precedent used for `unit_filter.py`).
*Selection:* unregistered v3 contract denied; registered -> a v3 result with `routing_authority = 'count_assessment'`, outcome = admission, and the section 3 checkpoint fields correct.
*Identity:* same record+config enqueued twice -> one item; threshold 10 vs 9 -> two items, different keys, both retained, same `record_sha256`; v1 vs v3 of one record -> different keys; an item enqueued under one config is denied if screened under another; `record_sha256` equals `digest(record)` on every item.
*History:* a second assessment of a record carries `related_assessments` to the first; no item contains `supersedes`; no earlier item changes by one byte; `assessment_history` imposes no recency; capture, observation and history records are untouched by any v3 run.
*Routing/gates:* each of the eight admissions maps as in section 5; a v3 result is never routed by `disposition` (the "12 flats to a hotel" case: v1 disposition `SUPPORTED...`, v3 `RETAIN_NOT_RESIDENTIAL_SUPPLY` -> no identity); tampered/unknown outcomes fail closed. For `ADMIT_SCHEME` **and** `ADMIT_FOR_ASSESSMENT`, extend the existing new-identity tests (`tests/test_discovery_ingestion_operational.py`, `tests/test_discovery_ingestion_acceptance.py`; exact cases confirmed at implementation) so every existing negative still denies/withholds identically (parent not COMPLETE, wrong subject, source URL/record-id mismatch, changed row, projector failure, unsupported facts -> `FACTS_WITHHELD` and no identity) and the positive path leaves `unit_facts NOT_WRITTEN`, status pending, no count, no `SchemeIntelligence`, no Site link, no `confirmed_qualifying`.
*Uncertain:* over the 24-record fixture and the 62 examples, `investigation_requirements` contains an entry for **every** reserved-matters result and **every** `ROUTE_COUNT_UNCONFIRMED` result (set-equality test, nothing silently dropped), each `executable: false`, `executor: 'NONE'`; no entry, report or field copies a parent figure into a proposed/approved total.
*Disable/rollback:* removing the registration makes v3 unusable; existing v3 items stay immutable and readable; v1 and v3 results both route through `routing_of`; nothing written outside existing ledger fields, so no database rollback exists to perform.

## 9. Deferred (kept as requirements; not in this slice)

- **Discovery and backlog handover.** Discovery progress stays separate from screening progress. A checkpoint per council **and** date basis, derived from COMPLETE `COUNT_RECONCILED` captures with the existing `completed_through`, starting from an **explicit, recorded coverage baseline**; failed windows remain outstanding gaps that block advancement; **partial observations never advance it** (asserted); ongoing windows start from verified coverage with an explicitly proposed overlap and identity-based duplicate handling (overlap length decided then; 029's 28 days applies only to the initial acceptance). Retrieving previously undiscovered historical applications (new windows, source requests, council authority) is a different path from re-screening retained records.
- **Re-screening retained captures** (new versioned, linked assessments; never overwriting) needs a SQL operation that can create children for a COMPLETE capture; held with Phase B. A read-only local recomputation report is also deferred.
- **Production path:** the SQL contract pin, owner grants (`contracts`, `completion_outcomes`), `operational_controller.py` gate, executable investigation task kinds, application promotion and count storage (035 Phase B/C).
