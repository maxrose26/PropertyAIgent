## Claims, recovery and stops

Control-row lock serialises decisions; PostgreSQL row locks avoid session advisory-lock hazards under pooling. SQLite takes a write reservation before reading eligibility. Source and writer effects require durable intent. Claims have bounded leases, monotonic fences, attempt bounds, exact authority and dependency checks. Every checkpoint/finish/materialised child validates ownership; stale workers cannot mutate them. A WRITE_INTENT is a durable barrier against other tasks. Shared B2 executes under the ledger control lock on PostgreSQL while its own separate transaction owns factual commit/readback. SQLite cannot validate this writer path and explicitly rejects it.

Crash before source/write intent: recover only after lease expiry and confirmed owned cleanup; resume the retained checkpoint under remaining authority and attempt budget. No source is repeated when a completed listing receipt exists. Abandoned source intent: blocked plus global stop because accounting/outcome is unknown. Abandoned write intent: PERSISTENCE_UNCERTAIN plus global stop. Lost writer or ledger acknowledgement preserves intent/barrier; no automatic retry, deletion or compensation. Successful B2 readback checkpoint followed by lost task completion can resume by comparing committed readback, without another write. There is no exactly-once promise across separate factual and ledger transactions.

Known RATE_LIMIT/SOURCE_UNAVAILABLE may defer3600s (including a durable council source cooldown) only for explicitly reviewed isolated contracts, CLOSED cleanup and certain accounting. Per-task max attempts1–3, finite grant and source-call counter remain required. Unsupported contract/no supported facts stay blocked. Unknown/TargetClosed/security/accounting/cleanup failures stop globally and explicitly mark the owned task blocked. The consumed Salford stop is never classified as a retryable transient. No automatic unblock/reconciliation endpoint exists.

Cleanup evidence and failure classification are trusted inputs from the supervisor/operator boundary; this library does not certify arbitrary callers. A production controller/role/authority boundary and kill switch require concrete operational acceptance. It is not a security API for untrusted agents.

## Migration, rollback and operations

Production migration is NOT authorised or executed. Proposed sequence: freeze exact migration/revision and access policy; verify existing DB/schema/default grants read-only; backup; run explicit additive install with approved migration owner; verify columns, PK/FK/checks, RLS/ACL and control record; grant a separately reviewed restricted worker role/policy only after acceptance. No grants to PUBLIC/anon/authenticated/service_role. FORCE RLS with no policies is default-deny; disposable superuser tests do not prove operational-role access. Schema is not included in application Base, so ordinary startup never creates or requires these tables.

Before population, empty-ledger rollback may drop only these two tables; populated-ledger rollback refuses. After population, disable consumers and revoke their access, preserve/export ledger and attempts, and roll code back. Never drop populated evidence or undo factual applications as queue rollback. A stale/uncertain intent must be reconciled before any worker restart.
