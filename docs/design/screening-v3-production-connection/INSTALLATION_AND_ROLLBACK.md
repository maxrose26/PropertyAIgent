# Screening v3: installation route and rollback (FOR LATER REVIEW; nothing here is authorised or executed)

**Status.** Documentation of the route a later, separately approved installation would take. This change installs nothing anywhere except in the disposable PostgreSQL of the CI rehearsal (`tests/test_ingestion_screening_v3_pg.py`). It prepares **no** live registration, **no** policy successor (decision D3 is held) and **no** owner mode.

## 1. What would be installed (R2) and what it is derived from

* One statement: `CREATE OR REPLACE FUNCTION public.ingestion_worker_step(...)`, generated by `verification/ingestion_storage/screening_v3_worker_sql.py` from the reviewed `docs/design/ingestion-operational-20261016/worker.sql` by six substitutions (undoing them reproduces the original byte for byte; asserted in `tests/test_ingestion_screening_v3_worker_sql.py`).
* It is the function the owner's `reviewed_inventories` treats as *original* in every accepted inventory state (`ORIGINAL`, `SUCCESSOR_POLICY_APPLIED`, `GENERATION2_*`, `GENERATION3_WINDOW_POLICY_APPLIED`). Installing it therefore needs a **new, named inventory state** in the owner's `verify_installed` (the window inventory with this one function replaced). That owner change, and the execution mode that would accept the state, are **not** part of this slice.
* v3 stays **default off**: nothing happens unless a registered grant lists `screening_configs` and a batch plan carries a `screening` binding, and a v3 child is never created over anything but a `LISTING_RECEIPT_V1` capture.

## 2. The existing owner-terminal route (unchanged shape)

The ceremony is the one the policy files use (`policy-window-allowance.sql` and its predecessors): in one transaction, with `lock_timeout 3s` and `statement_timeout 10s`, grant the owner role to the current user **temporarily and explicitly**, grant `CREATE` on the schema to the owner role, `SET LOCAL ROLE ingestion_storage_owner`, run the single statement, `RESET ROLE`, revoke `CREATE`, revoke the owner role from the current user, `COMMIT`. Runtime logins never receive the owner, issuer, barrier or recovery memberships.

**Preconditions, each read and recorded at ceremony time (never assumed from an earlier observation):**

1. The installed inventory is exactly the accepted one (`verify_installed`), function hashes identical to the reviewed inventory.
2. The control row is read and digested: its stop state (global stop, manual stop, generation) is exactly what the approving decision names. The ceremony **does not clear, reset or change any stop**.
3. No unexpired grant, no unresolved `WRITE_INTENT` barrier, no `PERSISTENCE_UNCERTAIN` item.
4. The script on the terminal hashes to the approved digest.

**Exact readbacks after `COMMIT` (all must hold, on a fresh connection):**

| Readback | Required |
|---|---|
| `sha256(prosrc)` of `ingestion_worker_step` | equals the derived body digest above |
| function owner | `ingestion_storage_owner` |
| function ACL | identical to the ACL read before the ceremony (execute for the worker and broker roles only; none for `PUBLIC`) |
| capability absence | `pg_has_role(current_user,'ingestion_storage_owner','USAGE'/'SET')`, the same for `ingestion_barrier_releaser`, and `has_schema_privilege('ingestion_storage_owner','public','CREATE')` are **all false** |
| other functions | inventory hashes of every other function unchanged |
| control row | digest equal to the digest read before (the ceremony writes no row) |
| rows | counts and a digest of every existing `ingestion_work_items` / `ingestion_work_attempts` row unchanged |

`READBACK_SQL` in `screening_v3_worker_sql.py` holds the first four queries; the disposable rehearsal runs them after installation and after rollback (it measured the ceremony at 0.011 s).

## 3. Rollback (exact)

Run `rollback_script()`: the same ceremony with the **original** function text (`CREATE OR REPLACE` of the statement taken verbatim from `worker.sql`). Required afterwards: the body digest equals the original (`3bdd5de9…445f`), owner and ACL unchanged, capability flags all false, every other readback of section 2 unchanged. The rehearsal proves this byte-for-byte, then proves v3 is refused again.

Rollback preserves evidence: it never deletes or edits a row. Any v3 children already created remain as inert, read-only data (their contract is in no grant; the v1 function cannot create or claim them), the capture and the earlier v1 assessments are untouched, and the bounded history query (a plain `SELECT`) still lists them.

**Rollback does not undo a registered authority.** An authority registered earlier is invalidated by the existing invalidation with a committed readback (R3/R4 steps, not part of this slice).
