## 2. What the observation is — and is not
It has **no committed mutation**. It is **not a strictly read-only observation** and must not be described as one. One database connection; 6 statements (limit 12); at most 20 database-active seconds and 30 supervised-active seconds after the 120-second hidden input; registration expiry ≤ 30 minutes; zero GitHub requests (bound 0), source requests, grants, exceptions, stop changes or credential changes; local audit only. It reads: stop generation, manual stop, `last_hard_stop`, global stop, a digest of the stop state and of the whole record, and the **names, expiry numbers and states** of every grant and Bolton exception (never bindings or key lists).

### The concrete exception for review — the one operation beyond reads
```sql
GRANT ingestion_storage_owner TO CURRENT_USER WITH INHERIT TRUE, SET TRUE;   -- inside an explicit transaction that is ROLLED BACK
```
Sequence: identity check → `BEGIN` → the `GRANT` → one `SELECT` of the control record (with the server clock) → `ROLLBACK` → capability readback (both `pg_has_role(... USAGE)` and `(... SET)` must be false).
* **Why:** the administrative identity has no table privilege on the ledger, and the only installed read-only function (`ingestion_acceptance_control()`) returns just the global stop, manual stop, generation and the count of unexpired grants. The accepted preflight and accepted invalidation readback already use this exact technique.
* **If it were ever committed** the migration identity's existing ADMIN-only membership in `ingestion_storage_owner` would gain inherit and set options (the owner's table privileges). Nothing commits it: the path contains no `COMMIT`.
* **On failure or disconnect between the GRANT and the ROLLBACK** PostgreSQL aborts the open transaction when the session ends, so it is never committed. The observer then **cannot read the absence back** (a second connection is not permitted); its result says `UNVERIFIED_TRANSACTION_ABORTED_BY_DISCONNECT_ABSENCE_NOT_READ_BACK` and it emits no observation record. If the route is a transaction pooler, you should confirm it rolls back an open transaction on client disconnect (not tested here: the disposable server is a direct connection).
* **Not done to avoid this:** no database function installed, no privilege broadened, no role created or altered.

Failed readbacks are asserted to be reported as **unverified**. Limits of this evidence: direct loopback connection (no pooler), hook-injected failures rather than a real process crash.

## 4. Kernel-check failures — root cause unresolved; separate maintenance proposal

## 5. Assessment for the next step (no execution proposed)
* **One-GET diagnostic vs owner-local capture.** A one-GET probe reproduces the exact failing request and, with the new transport object, answers what the council returns to that environment — the unresolved transport question. It cannot attribute a bad answer to the address; that needs the same probe from the owner-local environment (where earlier captures succeeded) as a paired control. An owner-local *capture* offers a more direct path to capture acceptance but answers nothing about the hosted route and would not be distinguishable from the earlier owner-local successes. Diagnostic evidence must stay distinct from capture-and-screening acceptance.
* **Why the stop must be observed before a combined candidate.** The installed policy (`ingestion_bolton_allowed`, `ingestion_register_bolton_exception`) honours or registers an exception only when the manual stop is empty or `STORAGE_TEST_STOP`, the generation matches the exception's, and (for registration) the generation is 0 or 1, the `last_hard_stop` and checkpoint digest are the pinned 18 October values, and fewer than three exception keys exist. Under generation 2 none can be honoured or registered; the owner readback, registration, qualification and cleanup code also hard-code generation 1 and `STORAGE_TEST_STOP`. Any change must be an **exact named single-use allowance bound to the observed stop state** (generation, strings, digest) without resetting the generation, removing historical exceptions or changing the cap broadly; the exception count and the digest are exactly what the observation returns. I have therefore **not** prepared that policy/contract candidate: its exact values depend on the observation, and preparing it first risks pinning guessed values.
