## Decision: buyer-relative requirements, not a universal quantity

Each mandate supplies its own AH minimum, maximum, range, or no quantity requirement. Fifty was the prior walkthrough example, not a platform minimum. Qualified exact counts use the actual boundary without tolerance. For independently qualified approximate counts without source bounds, the inclusive investigation band is 0.9–1.1 times each relevant buyer boundary; explicit ranges/one-sided bounds are never expanded. A component can establish a minimum but cannot establish a whole-scheme maximum merely because its own count is below that maximum.

Legacy figures remain reported; source and scope unverified, accessible for investigation, outside qualified numeric matches and confident claims from those numbers. Unknown is not zero. The accepted legacy30/alternative490 repair and separate reported-count CSV column remain intact.

## What caused STRONG_FIT at the base commit?

The old harness called `assess_buyer_fit(profile, facts)` directly with no B2 context. It copied HOUSING_ASSOCIATION, removed its maximum300, left its illustrative minimum50, and supplied a local retirement preference. Copied narrative notes still mention the template range; the matcher reads structured fields, not those notes. It did not evaluate a real persisted buyer.

Classification is not a vote or score: any hard mismatch gives NOT_SUITABLE; otherwise a blocking unknown gives INSUFFICIENT_EVIDENCE; otherwise STRONG_FIT. STRONG_FIT is deterministic mandate fit, not the separate Acquisition Agent taxonomy PURSUE/INVESTIGATE/MONITOR/NOT_RELEVANT and not proof of availability.

The old category follows the compatibility-mode code, but the old report overstated completeness by omitting the context limitation. The existing supported application entry point is `buyer_matching_b2_context.evaluate_buyer_fit`, which requires context or enough identity to construct it. The harness now builds context using `build_b2_context_for_planning_delivery` on its own disposable database, evaluates via that supported entry point and supplies the same context to packet assembly. This repairs the acceptance harness rather than changing the global category taxonomy to compensate for a missing caller input.

The complete local run retains STRONG_FIT for ACCEPT. This is justified as mandate fit under these specific structured requirements: relevant count/product/planning, supported package type, no geographic restriction, no hard control/progress/tenure requirement. It is not a general claim that two matching fields establish a purchasable opportunity. Unknown geography under a restricted mandate blocks fit; a known out-of-area council excludes; unknown required planning blocks; general specialist exclusions continue to dominate. Above-maximum behaviour remains the existing investigation exception, not a newly invented hard rejection.
